NV12：一帧视频怎样装进内存

一课目标：给定 width 与 height，算出一帧 8-bit NV12 的 Y、UV 与总字节数，并解释为什么不能把 row stride 当成可见宽度。

视频课 0006 · 为 Learning「视频·采集」做前置 · issue 07 · ADR-0006 · 速查 · 对仗 0001 PCM≠WAV

先建立一个画面直觉

摄像头送来的是未压缩的 Raw Video Frame：每个位置有亮度样本，还有一组共享的颜色偏差样本。它不是 JPEG / H.264，也还没有经过「编码」这一站。

NV12 是 8-bit 4:2:0 的两 plane 布局。先看形状，暂不看颜色转换： 

Y plane       width × height 个 Y
              Y00  Y01  Y02  Y03 …
              Y10  Y11  Y12  Y13 …

UV plane      (width/2) × (height/2) 个 UV pair
              U00  V00  U01  V01 …
              U10  V10  U11  V11 …

4:2:0 表示 chroma 横向减半、纵向也减半：一个 U/V pair 服务原图中的 2×2 四块 luma。 Microsoft 的 YUV 采样说明 把这一点写得很直接；NV12 的 Y 在前、交错 U/V 在后的布局见 NV12 一节。

字节账：12 bits / pixel 从哪里来

Y = width × height × 1 byte UV = (width/2) × (height/2) × 2 bytes 总 = width × height × 1.5 bytes

这里的 ×1.5 只对 8-bit 4:2:0 成立。它不是「所有视频」的常数，也不是压缩率。Apple 420v 对本仓库还多一层含义：8-bit video range。Apple SDK 的 CVPixelBuffer.h 写明 Y 名义范围是 16–235、Cb/Cr 是 16–240；这与 RGB 的 0–255 不同，预览时必须按正确颜色语义转换。

亲手算：改 width、height 或 stride

NV12 frame lab

先点 720p 预设。再把 Y stride 改成 1408、UV stride 改成 1408，观察「tight frame」与「allocated」为何不同。

Y plane · 1280 × 720 921,600 B
UV plane · 640 × 360 UV pairs 460,800 B
tight frame1,382,400 B
allocated with stride1,382,400 B
row padding0 B

最容易踩的坑：stride 不是 width

CVPixelBufferGetBytesPerRowOfPlane 返回的是「分配器实际每行跨多少字节」。它可能大于可见宽度，因为硬件 / 对齐会在每行尾部留 padding。 Apple 文档 和 plane base address 要成对使用。 

正确：plane0 每行只复制 width bytes
      plane1 每行只复制 (width/2) × 2 bytes

错误：把 base address 后面的一大段连续内存
      直接 memcpy 成 width × height

Issue 07 要写 tight-packed 文件，所以复制时必须按可见宽度逐行读，跳过每行末尾的 padding。你可用本页 lab 的「720p padded」预设看到差额：每帧分配区会比 tight 帧多出若干字节；那些字节不属于画面。

技能：检索练习

测验

1. NV12 的 UV plane 每行有多少个 UV pair？
2. tight 1280×720 8-bit NV12 一帧多少字节？
3. 从 padded CVPixelBuffer 写 tight 文件应怎么复制？

动手（两分钟）

  1. 在 lab 里先记下 720p tight 的 1,382,400 B。
  2. 切成 720p padded，记下 allocated 与 row padding 的差额。
  3. 把 width 改成 640、height 改成 480，先心算再让 lab 给答案。
