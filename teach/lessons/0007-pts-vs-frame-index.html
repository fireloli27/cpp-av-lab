第 3 帧不一定是第 100 ms

一课目标：分清 frame index、Presentation Timestamp（PTS）、duration 与 callback 到达时刻，并能从相邻 PTS 判断是否发生了时间空洞。

视频课 0007 · 承上 0006 NV12 字节账 · ADR-0006 · issue 07 · 时序速查

先取回上一课的锚

NV12 的 tight 帧字节账是后续时序表的「每帧载荷量」。1280×720、8-bit 4:2:0 时，Y plane 是 921,600 bytes，UV plane 是 460,800 bytes。

四个时刻不要混成一件事

名字回答的问题本仓库例子
frame_index本次成功收到第几帧0, 1, 2, 3…
source PTS这张画面属于来源时间轴哪一刻manifest 的 pts_ns
duration这个 media sample 覆盖多长时间可以 unknown / invalid
callback arrival进程何时轮到执行回调不作为媒体时间

Apple 的 CMSampleBufferGetPresentationTimeStamp 返回 sample buffer 中最早的 presentation timestamp；失败时返回 kCMTimeInvalid。本采集路径每个视频 buffer 一张帧，因此它就是我们写入 manifest 的来源 PTS。

PTS 不是 callback 的执行时刻。操作系统可能在 PTS=100 ms 的画面之后，晚几毫秒才让 delegate queue 执行它；排队延迟改变「何时处理」，不改变这张画面在媒体时间轴上的坐标。

CMTime 怎样变成整数纳秒

CMSampleBuffer
  → CMSampleBufferGetPresentationTimeStamp()
  → CMTime(value, timescale)

seconds = value / timescale
pts_ns  = round(seconds × 1_000_000_000)

例如：CMTime(1, 30)
     = 0.033333… s
     ≈ 33,333,333 ns

实现时应转成 int64_t 纳秒并检查 CMTIME_IS_VALID。Issue 07 的 manifest 同时记录 pts_ns 与 relative_pts_ns，后者等于 pts_ns - first_pts_ns，所以首帧固定为 0。

交互：从时间差找空洞

PTS timeline lab

先看稳定 30 fps，再切到「第 3 帧前丢了一帧」。观察 frame_index 仍连续，但 PTS 的相邻差值变大。

0 ms33 ms67 ms100 ms133 ms
frame_indexpts_nsrelative_pts_nsΔ previous

在 dropped 场景里，frame_index=3 的 PTS 约为 133 ms，而前一帧约为 67 ms，差值是 66.7 ms。帧序号只说「这是我收到的第四帧」；它无法回答「本来 100 ms 附近是不是少了一张」。

duration 为什么不能乱补

CMSampleBufferGetDuration 返回 sample buffer 的 duration，但 duration 可能 invalid / unknown。即使只知道目标 30 fps，也不能在下游把每次 frame_index 增量都伪装成精确 33.3 ms；真实 PTS 才能暴露丢帧与不均匀间隔。

为什么 callback 里不要写 1.38 MB 文件

AVCaptureVideoDataOutput 的 delegate 在指定 queue 上回调。queue 被文件 I/O 或颜色转换堵住时，late video frames 可能被丢弃。Apple SDK 的 AVCaptureVideoDataOutput.h 对 alwaysDiscardsLateVideoFrames 的说明就是这个边界；issue 07 因此要求 callback 只复制 tight NV12 与 PTS，写盘放到采集结束后。

摄像头帧时间轴：PTS 0 → 33 → 67 → [100 丢失] → 133 ms callback queue： 可以晚处理，但不能把 PTS 改写成自己的执行时刻

A/V 同步只点名

A/V 同步要把音频和视频放到可比较的呈现时间轴上；它通常发生在接收、jitter buffer 与播放调度一带。07 的单视频采集只保留 PTS，不证明独立录制的 audio 与 video 已同步。

技能：检索练习

测验

1. 热身题：tight 1280×720 NV12 一帧多少字节？
2. CMSampleBuffer 的 PTS 最准确回答哪个问题？
3. dropped 场景里 frame_index=3 的 PTS 是 133 ms，前一帧是 67 ms，说明什么？

动手（两分钟）

  1. 打开 dropped 场景，自己从表里写出 pts_ns、relative_pts_ns、Δ previous。
  2. 切到 jitter 场景，判断它是否一定等于「丢了一帧」。
  3. 用自己的话解释：为什么 callback 延迟不要求改写 PTS。

判断标准：看到「frame_index 连续」不能直接说「没有丢帧」；必须比较 PTS。看到「PTS 间隔变大」也要区分 scheduler jitter 与实际缺席，不能只凭一个差值断言。
