采集仍是 C++，会话活在 .mm

一课目标：指出这次视频采集里哪一段必须是 Objective-C++，哪一段仍是 C++，以及 delegate 回调为什么只拷贝、不写盘。

视频课 0008 · 承上 0007 PTS · ADR-0006 · 课记 · 语言缝速查

音频能停在 .cpp

音频五段调用的是 AudioToolbox 的 C 接口，例如 AudioQueueNewInput。C 接口可以从 .cpp 直接调用，所以那些实验没有 Objective-C 源文件。

这次的会话类型是 Objective-C 类

ADR-0006 选定 AVCaptureSession 与 AVCaptureVideoDataOutput。 Apple 文档里它们是 Objective-C 类：要 alloc / init，要用 delegate，权限请求走 block。没有对等的公开 C 函数。调用它们的文件因此是 main.mm。

.mm 是 Objective-C++，不是把实验改成另一门语言。main.mm 里仍然调用 C++ 的 pack_nv12_planes_to_tight 和 publish_capture_artifacts。

.cpp nv12.cpp、test_video_capture.cpp 不创建会话、不打开摄像头 .hpp capture_publish.hpp 两边共用的 C++ 声明 .mm main.mm、capture_publish.mm 只有这里碰 AVFoundation / Core Image

Catch2 链的是静态库里的 C++ 写盘契约。测试进程不链接摄像头，所以无摄像头的 check-learning.sh 仍能通过。真机画面只在短文的人工烟测里验收。

回调结束之后，才把字节交给写盘

默认摄像头
  → AVCaptureVideoDataOutput 的 delegate（serial queue）
       校验 420v 与 1280×720
       拷贝 tight NV12 + PTS          ← 仍不写文件
  → 凑满 --frames，或 15 s 超时
  → publish_capture_artifacts
       staging → 替换 out/video/capture/

alwaysDiscardsLateVideoFrames 为 YES 时，delegate queue 来不及取走的帧会被丢掉。在回调里写 1,382,400 字节的文件，或做 PNG 颜色转换，都会把这个 queue 堵住。所以文件 I/O 和 Core Image 预览都在采集结束之后。

先钉住 720p，再挂上 delegate

课记记录了本机 FaceTime 摄像头上的现象：只设 AVCaptureSessionPreset1280x720 不够，startRunning 会把 activeFormat 打回 1920×1080。若这时 delegate 已经在收帧，第一张 1080p 会让整次采集失败。 

commitConfiguration
  → startRunning
  → 再次 lockForConfiguration，钉 1280×720 / 30 fps
  → 然后才 setSampleBufferDelegate

这是这次实现里用烟测钉下来的顺序，写在课记「踩坑与边界」。格式数字仍以课记契约为准，教室不另写一套。

这节不证明的事

保存下来的是 Raw Video Frame 和它的 PTS。编码库还没选。A/V 同步仍在接收/播放一带，本阶段没有把音频时间轴和视频时间轴对齐。

测验

1. 采集入口为什么是 main.mm？
2. delegate 回调里这阶段允许做什么？
3. 本机上 setSampleBufferDelegate 应放在哪一步之后？

动手（两分钟）
