# 管线旁路与职责边界

本篇是毕业叙述，没有实验入口，也没有可勾的运行步骤。Learning Pipeline Stages 仍然只有五段。下面这些模块要能放进管线里讲清楚；动手调通它们是加分包，缺了不影响 Learning Exit Criteria。

音、视两条已经跑通的路径见 [audio/pipeline.md](./audio/pipeline.md) 与 [video/pipeline.md](./video/pipeline.md)。那两篇证明的是离线文件接力。本篇讲的是真实通话里还得有、但学习实验故意没做的东西，以及谁负责哪一段。术语以根目录 `GLOSSARY.md` 为准。

## 旁路放在哪

四件旁路都不是五段之一。学习实验里的固定码率、UDP 环回、音频输出缓冲、视频 200 ms PTS 夹断，都不能拿来冒充它们。

### AEC

回声消除在**发送侧**，采集之后、编码之前。麦克风会把扬声器正在放的远端声音再采进来；AEC 用渲染路径上的参考信号估计这段回声，再从近端采集里减掉。参考信号取自音频渲染，不取自视频窗口。

本仓库的音频采集直接把 PCM 写进 WAV，编码前没有这一步。视频路径不产生回声参考。

### 弱网码率自适应

它卡在**网络反馈和编码器之间**。接收侧或发送侧根据丢包、延迟估计当前能承受的码率，再让编码器降码率、降分辨率或降帧率。它改的是编码这一段的目标，但触发它的是传输之后的反馈，不是采集。

学习实验把音频钉在 64 kbps、视频钉在 2 Mbps，没有反馈回路。固定码率只说明「这一段可以压出码流」，不说明拥塞时会让路。

### jitter buffer

它在**接收之后、解码之前**。网络到达间隔是抖的，解码器更希望按比较稳的节奏拿 access unit。jitter buffer 把提前到的包先攒住，并在缺口处做丢包隐藏或等待。音频和视频各有自己的缓冲；它们吸收的是网络抖动，不是本机调度抖动。

不要把它和这两件事混在一起：

- 音频渲染里 3 个 AudioQueue buffer 是**输出缓冲**，对付的是设备回调和线程调度。
- 视频渲染里超过 200 ms 的 PTS 夹断只是不让窗口被一条异常时间戳卡住，包没有经过网络。

本地传输/打包是本机环回，没有人为丢包，也没有 jitter buffer。

### A/V 同步

它在**接收 / 播放**这一带。音频按输出设备的时钟往外放，这只钟当主钟；视频帧按自己的 Presentation Timestamp 被提前、推迟或丢掉，好跟这只钟对齐。它不在采集里做，也不是把两路文件用同一个帧率各播各的。

本仓库的音频渲染和视频渲染是两次分开的进程：一个交给声卡，一个按视频自己的 `relative_pts_ns` 刷新窗口。两条都跑通，仍然没有音画对齐实验。

## 五段分别落在谁身上

```
Host App ── Call Signaling ──► 对端 Host App / 既有 IM
   │
   └── 嵌入 Client AV SDK
         采集 →（AEC）→ 编码 → 打包/发送
                                    │  弱网反馈，回头改编码码率
                                    ▼
         渲染 ←（A/V 同步）← 解码 ← jitter buffer ← 接收
                                    ▲
                                    │ Media Signaling（承载通道未决）
                                    ▼
                                  SFU：转发已编码的流，基本不解码混画
```

**Client AV SDK** 盖住客户端这一侧的五段：采集、编码、把码流送出去、收回来、解码、渲染，再加上面四个旁路，以及和 SFU 之间的 Media Signaling。它不是面向终端用户的通话 App，也不自建 Call Signaling。学习实验是在 macOS 上把五段拆开跑通，不是这个 SDK 的产品实现。

**Media Server（SFU）** 站在已经编码的媒体面上，把各路流转发给订阅者。它基本不解码、不混画，所以采集、AEC、渲染、A/V 同步都不在它里面。它也不兼任 Call Signaling。弱网码率自适应的估计可以来自转发路径上的反馈，但「把像素变成码流」和「把码流变回画面」仍在客户端。

学习工程没有 SFU 进程。环回只代替「编码之后、解码之前」那一段传输，而且只在本机。

## 两种信令

**Call Signaling** 是呼叫生命周期：邀请、振铃、接听、拒绝、挂断、进房、离房。它归 **Host App**，走既有 IM 通道。SDK 消费已经建立的通话或房间上下文，不自己做这条通道。

**Media Signaling** 是 SDK 和 SFU 之间的媒体面协商与控制：媒体描述、传输候选、订阅和转发。它和 Call Signaling 不是同一个词。把 SDP 或 ICE 塞进 IM 消息里、又不加区分，会把两条通道搅在一起。

Media Signaling 的承载通道（复用 IM、独立 WebSocket 或 HTTP、随媒体通道，或其他）是 spec 未决 #1。本篇不选。

## 本篇不证明什么

- 不证明 AEC、弱网码率自适应、jitter buffer、A/V 同步已经调通。动手是加分包。
- 不证明产品「打包」必须是 RTP。学习音频用了长度前缀，学习视频把同一个 Transport Unit 拆成 UDP 分片；spec 未决 #5 仍开。
- 不证明 Media Signaling 走哪条连接，也不证明 SFU 自研还是改造开源。
- WebRTC / libwebrtc 里这些概念叫什么，见 [webrtc-crosswalk.md](./webrtc-crosswalk.md)。改得动那棵源码树不是毕业条件。
