# Product Hypotheses

产品愿景假设册。条目均为**假设**，非正式工程承诺。  
「验证钩子」指向 Learning Project 中可用来证伪/加强该假设的实验或叙述验收；钩子标为「学习阶段不可验证」者，不得在学习工程里假装已拍板。

关联定稿：`.scratch/learning-project/spec.md`、根目录 `GLOSSARY.md`。

---

## 假设表

| ID | 假设 | 验证钩子（学习工程） |
| ---- | ------ | ---------------------- |
| H1 | 最终交付形态是嵌入式 **Client AV SDK + Media Server**，供 **Host App**（IM/社交）集成，而不是独立通话 App 或纯云 RTC 转售 | **叙述验收**：短文/总述能画清 Host App、SDK、SFU 边界；无单一阶段实验可「证明」商业形态，仅能保持文档与假设一致 |
| H2 | **Call Signaling** 由 Host App / IM 主导；SDK 消费已建立的通话/房间上下文 | **叙述验收**（必写清）；可选加分：双端互通实验里用「写死/脚本化房间上下文」代替真实 IM，以演示 SDK 不拥有呼叫状态机 |
| H3 | **Media Signaling** 与 Call Signaling 分离，发生在 SDK ↔ SFU 之间 | **叙述验收**（必写清）；**加分：SFU 实验** 若做，须出现独立于呼叫信令的媒体控制/协商步骤。承载通道见 U1 |
| H4 | 产品场景以 **1v1 + 小群多方（约 ≤9）** 的 **Call** 为主，不以大房间/直播为默认 | **加分：SFU 实验**（多路订阅/转发直觉）；硬五段实验不验证人数上限。人数「约 ≤9」本身见 U2 |
| H5 | 默认 **Call Media** = 麦克风音频 + 摄像头视频；屏幕共享非核心 | **硬实验**：音、视各至少一条 Learning Pipeline Stages 全路径；屏幕共享不做硬实验 |
| H6 | 产品 **Target Platforms** 优先 Android + iOS；macOS 是学习/调试宿主 | **学习工程**：全部硬实验在 macOS 宿主完成；移动绑定 **学习阶段不可验证**（正式工程） |
| H7 | Media Server 形态假设为 **SFU**（选择性转发），不兼任 Call Signaling | **叙述验收**（必写清 SDK vs SFU 覆盖段）；**加分：SFU 实验** 用于加强/证伪「需要转发服务器」的直觉。MCU/无服务器见 U3 |
| H8 | **Stack Posture** = 能力自研、协议可复用成熟栈（可基于 WebRTC/开源 SFU），对外仍是自有 SDK + 自有 Media Server | **硬要求（与 Learning Exit Criteria 对齐）**：≥1 篇 WebRTC 对照短文（五段及叙述必会旁路的模块映射）。**不以**改得动 WebRTC 为验证成功。具体开源选型见 U4；对照材料基线见 U9 |
| H9 | 部署形态（私有化 / 公有云多租户）**有意延后**，不锁死愿景 | **学习阶段不可验证**；见 U5 |
| H10 | 默认不做：大房间/直播、屏幕共享核心化、自建 Call Signaling、从零重造完整 RTC、录制、美颜、IM 本身、E2EE 早期必达 | **过程约束**：学习短文与实验选题不把上列当硬范围；若加分包触及，须标明「非产品默认愿景」 |
| H11 | 真实通话中 **AEC** 位于采集后、编码前的音频处理一带，是产品必谈能力，但不是「五段之一」 | **叙述验收**（毕业必会说明位置与作用）；**加分：AEC 调参实验** 可加强，不硬性 |
| H12 | **弱网码率自适应** 依赖网络反馈作用于编码码率/发送，是产品必谈能力，但不是「五段之一」 | **叙述验收**（毕业必会说明位置与作用）；**加分：网络真实感 / 弱网自适应动手** 可加强，不硬性 |
| H13 | 接收侧需要 **jitter buffer** 吸收网络抖动，是产品必谈能力，但不是「五段之一」 | **叙述验收**（毕业必会说明位置与作用）；**加分：动手实验** 可加强，不硬性 |
| H14 | 音视频一同呈现时需要 **A/V 同步**，是产品必谈能力，但不是「五段之一」 | **叙述验收**（毕业必会说明位置与作用）；**加分：动手实验** 可加强，不硬性 |
| H15 | 学习资产应能迁移到正式工程：术语、管线分段、SDK/SFU/两种信令边界、WebRTC 模块对照 | **硬交付**：五段实验短文 + WebRTC 对照短文完成后，做一次「正式工程开工检查清单」式自检（叙述/文档验收） |

## 未决事项（不代为决定）

| ID | 未决问题 | 备注 |
| ---- | ---------- | ------ |
| U1 | Media Signaling 的**承载通道**如何选？ | 复用 IM / 独立 WS 或 HTTP / 随媒体通道 / 其他；H3 只锁定「与 Call Signaling 分离」 |
| U2 | 小群人数上限是否就取 ≤9，还是另定？ | H4 中「约 ≤9」来自愿景假设，非测量结论 |
| U3 | 是否允许长期保留「1v1 P2P、多方再上 SFU」的混合媒体路径？ | 与 H7 的「愿景默认 SFU」可能张力，需正式工程前另决 |
| U4 | Client 侧以哪条 WebRTC/替代栈为主？SFU 以哪条开源或自研比例为主？ | H8 只锁定姿态 + 学习侧对照短文硬要求，不锁定仓库与许可证选型 |
| U5 | 部署与运维模型 | H9 已声明延后 |
| U6 | 屏幕共享、录制、美颜、E2EE 若业务强需求，何时升格进愿景？ | 当前在 H10 默认排除 |
| U7 | 产品级 AEC / 弱网自适应 / jitter buffer / A/V 同步的质量条与是否自研 | H11–H14 只锁定「要会说明位置与作用 + 学习非硬实验」 |
| U8 | Host App 与 SDK 的通话上下文 API 形状（进房参数、成员列表、挂断所有权等） | 学习阶段可用假数据；正式集成契约未定 |
| U9 | WebRTC 对照短文所针对的发行版 / 文档基线 | H8 硬要求「有对照短文」，不指定读哪一版 |
| U10 | 学习阶段 3「打包」是否必须是 **RTP 打包**？ | 允许自定义包 / 容器帧 / 长度前缀分帧等替代方案是否可接受，由你另决；拍板前环回只要求可发送/接收的数据单元 |
